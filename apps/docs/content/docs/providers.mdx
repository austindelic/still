---
title: Providers And Backends
description: How Still chooses where packages and tools come from.
---

Still uses backends to fetch and install different kinds of software. A backend is the part of the engine that knows how to resolve metadata, download artifacts, verify them, and place files where Still expects them.

The current engine path focuses on Homebrew formula data. The v1 backend list is broader and is kept here so config examples have a clear destination.

## Current Path

Homebrew formula support is the most developed path today. It gives Still access to a large package catalog while the engine handles its own install layout.

```bash
still install ripgrep
```

Behind that command, Still looks up formula metadata, downloads a bottle, extracts it, and tries to link or report the installed binary.

## V1 Backend Families

Planned v1 backend families:

- `core` or `native` for first-party Still installers and platform behavior
- `github` for GitHub releases, tags, and release assets
- `http` for direct URL downloads with checksum verification
- `cargo` for Rust crates installed through Cargo
- `go` for Go tools and modules
- `npm` for Node packages
- `pipx` for Python CLI tools
- `asdf` for the existing asdf plugin network
- `aqua` for Aqua registry packages

Backend-specific work belongs behind a common engine interface. Config parsing should produce typed package and tool requests first; backend selection comes after parsing and before install planning.

## Choosing A Backend

Use `backend = "auto"` when you want Still to pick the right source.

```toml
[packages.postgresql]
version = "16"
backend = "auto"
```

Use an explicit backend when the source matters to the project.

```toml
[tools.pnpm]
version = "latest"
backend = "npm"
```

Explicit backends make reviews easier. Auto backends keep common configs shorter.
